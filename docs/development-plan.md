# go-sqldb 开发计划

## 目标
在保持项目“简洁教学型数据库”定位的前提下，优先提升并发安全、执行稳定性与语义正确性，再逐步扩展能力。

## Phase 1：稳定性与并发安全（1-2 天）

### 1. 并发读写保护
- 在表级引入 `sync.RWMutex`。
- `SELECT` 走读锁，`INSERT` 走写锁。
- 重点覆盖 HTTP 并发请求场景，避免 `Pager.Pages` 与 B+Tree 修改时出现数据竞争。

### 2. 入口错误处理修复
- 修复 `/exec` 路径中 `ParseInsert` 后未及时判断错误的问题。
- 保证解析失败时立即返回，不再进入执行计划。

### 3. Pager 边界逻辑修复
- 修正页加载边界判断，避免读取文件末尾边界页时出现不一致行为。
- 明确空白新页分配路径，确保 `GetPage` 不返回无效页对象。

### 4. 回归与竞态验证
- 执行：`go test ./...`
- 执行：`go test -race ./...`
- 新增最小并发用例（并发 INSERT/SELECT），确保基础链路稳定。

---

## Phase 2：SQL 语义与执行正确性（2-3 天）

### 1. WHERE 计算器重构
- 移除基于 `types.Eval` 的表达式执行。
- 实现受控 evaluator（先支持 `= != > >= < <= AND OR`），避免表达式注入与语义漂移。

### 2. 字符串字面量规范化
- 统一 INSERT 字符串处理（引号剥离、转义规则一致化）。
- 明确存储层与展示层的字符串约定，避免当前“值保留引号”的不一致。

### 3. 测试补齐
- 为 parser/planner 增加非法输入与边界条件测试：
  - 列数不匹配
  - 类型不匹配
  - 非法 WHERE 组合
  - LIMIT 异常值

---

## Phase 3：存储可靠性（2-4 天）

### 1. 最小可用恢复机制
- 引入轻量 WAL 或 journaling（建议先做 append-only redo）。
- 明确写入顺序与崩溃恢复流程。

### 2. Flush/Close 一致性增强
- 统一处理多页刷盘错误（错误聚合与可观测输出）。
- 保证关闭流程在部分失败场景下行为可预测。

### 3. 崩溃恢复测试
- 增加“写入中断 -> 重启恢复 -> 一致性校验”测试。

---

## Phase 4：功能扩展（按需）

### 1. DDL 最小支持
- 优先考虑 `CREATE TABLE` 最小子集，或先支持“可配置 schema”。

### 2. 查询性能优化
- 主键条件优先走 `seek`，减少全表扫描。
- 保留 Volcano 模型结构，逐步引入更清晰的算子边界。

### 3. 可观测性增强
- 增加慢查询日志、基础页命中率统计、错误计数。

---

## 里程碑与验收建议

### M1（Phase 1 完成）
- `go test ./...` 通过
- `go test -race ./...` 无 data race
- 并发请求下无崩溃/明显错乱

### M2（Phase 2 完成）
- WHERE 不再依赖 `types.Eval`
- SQL 语义测试覆盖核心表达式
- 字符串行为一致并有测试保护

### M3（Phase 3 完成）
- 具备最小崩溃恢复能力
- 恢复链路有自动化测试

### M4（Phase 4 按需完成）
- DDL/优化/可观测性按优先级逐步落地

---

## 推荐执行顺序
1. 先做 Phase 1（先稳住并发与边界）
2. 再做 Phase 2（收敛 SQL 语义）
3. 然后做 Phase 3（提升存储可靠性）
4. 最后按需求推进 Phase 4（能力扩展）
